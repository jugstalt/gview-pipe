# 37. SFTP

Date: 2026-11-03 · Status: accepted

## Context

Partners often exchange files over SFTP. With the File Trigger ([ADR 0036](0036-file-trigger.md)) and Read/Write File a workflow can handle local folders, but it can't fetch or deliver files on a server.

## Decision

- A separate plugin **`gView.Pipe.Plugins.Sftp`** with the library SSH.NET (MIT), installed like the other external plugins. SFTP only; FTP and FTPS are not part of it.
- Credential **SFTP Server** (`90e8ec4b-32b6-4a55-9798-e04a3369b8a3`): *Host*, *Port* (22), *User name*, *Password*, *Private key* (PEM or OpenSSH, multi-line), *Passphrase* and *Host key fingerprint* (SHA-256, e.g. `SHA256:abc…`). The three secrets are secret fields and can come from a source ([ADR 0033](0033-external-secrets.md)). Password or key, at least one of them; both are tried in this order: key, password.
- **The fingerprint is required.** A server whose host key has another fingerprint is refused, and the message names the fingerprint the server presented, so an admin can check it and enter it. No server is trusted blindly.
- One node **SFTP** (`2c85ff47-8cf5-4aec-9c08-04f38b56d20a`, Category Files) with the *Operation* List, Download, Upload, Delete or Rename. It runs once per input item, and paths accept expressions. Settings that an operation does not use are ignored.
  - **List:** *Path* (a folder), *File pattern* (`*`), *Include subfolders*, *Include directories*. One item per entry: `fileName`, `path`, `size`, `modifiedAt`, `isDirectory`. More than 10000 entries is an error, so nothing is missing silently.
  - **Download:** *Path* of one file, no patterns. The output is the input item with `fileName`, `path`, `size`, `modifiedAt` and the content as attachment (*Binary property*, default `data`). A file larger than *Max file size (MB)* (default 100) is refused before it is loaded.
  - **Upload:** the attachment of the item goes to *Path*. A file that exists is an error unless *Overwrite*; missing folders are an error unless *Create folders*. The content goes to `<name>.part` first and is renamed when complete, so a reader never sees half a file. With *Overwrite* the old file is deleted just before that rename.
  - **Delete:** *Path* of a file; a missing file is an error.
  - **Rename:** *Path* to *New path*, also to move. A target that exists is an error unless *Overwrite*.
- Local files are not touched: content comes and goes only as the attachments of items. Read File and Write File connect it to the folders released with `Pipe:FileRoots`.
- **One connection per run of the node,** opened when the first item needs it, used for all items and closed at the end. *Timeout (seconds)* (default 30) applies to connecting and to each operation. Stopping the run closes the connection.
- The connection is behind an interface (`ISftpConnector`), so the node is tested without a server; the SSH.NET part is a thin adapter.

## Consequences

- No pool of connections across runs: no state, no cleanup, no trouble with changed credentials. A workflow with many items per run is fine; many runs with one item each reconnect each time.
- Moving a file to a path that exists with *Overwrite* is not atomic (delete, then rename).
- The adapter to SSH.NET is not covered by tests that talk to a real server.
